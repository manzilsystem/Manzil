# خطة تطوير مساعد عم عبده: اللهجات والأسئلة المركبة وRLS

## ما نُفّذ في هذه المرحلة

- تطبيع صيغ مصرية شائعة قبل تصنيف النية، مثل «دلوقتي»، «الفلوس راحت فين»، «مين لسه مادفعش»، و«دفعوا إزاي؟».
- ربط العبارات السابقة بالنوايا الموجودة بدل إنشاء مسار خاص لكل صيغة.
- توسيع الإجابة المركبة لتجمع السيولة والمصروفات والمتأخرات وطرق التحصيل في رد واحد.
- إضافة اختبارات وحدة للهجات والأسئلة المركبة.
- إضافة فحص ثابت لسياسات جدولَي `assistant_conversations` و`assistant_messages`.

## خارطة التنفيذ المقبلة

### المرحلة 1 — قاموس التطبيع

يُضاف كل تعبير جديد إلى طبقة التطبيع فقط عندما يكون معناه واضحًا ولا يغيّر معنى كلمات مالية أخرى. أمثلة المجموعات:

- الزمن: «دلوقتي»، «حاليًا»، «الشهر اللي فات»، «من البداية خالص».
- السؤال عن الإنفاق: «الفلوس راحت فين؟»، «اتصرفنا في إيه؟»، «إيه اللي اتدفع؟».
- المتأخرات: «مين لسه مادفعش؟»، «مين عليه فلوس؟»، «مين متأخر؟».
- السيولة: «الخزنة فيها كام؟»، «كام في الصندوق؟»، «الرصيد عامل إيه؟».
- التحصيل: «دفعوا إزاي؟»، «اتدفعت بإيه؟»، «طرق التحصيل إيه؟».

تُراجع كل إضافة باختبار موجب واختبار سلبي حتى لا تتحول عبارة المالك إلى سؤال إداري أو العكس.

### المرحلة 2 — محلل الأسئلة المركبة

يبحث المحلل عن أكثر من نية مستقلة في السؤال، مع دعم الروابط «و»، «وكمان»، «بالنسبة لـ»، «عايز أعرف ... وبعدها ...». لا ينفذ عمليات كتابة داخل الرد المركب؛ العمليات المالية والإعلانات تظل معاينة منفصلة وتتطلب تأكيدًا صريحًا.

قواعد السلوك:

1. الاحتفاظ بفترة السؤال المشتركة لكل الأقسام.
2. إزالة النوايا المكررة، مع إبقاء ترتيب ظهورها.
3. عرض كل قسم بعنوان مستقل قابل للقراءة.
4. إذا كان جزء من السؤال غامضًا، عرض الأقسام المفهومة وطلب تحديد الجزء الغامض.
5. احترام نطاق المالك قبل التحليل المركب؛ سؤال المالك عن الخزنة أو تقرير العمارة لا يتحول إلى تسريب جزئي.

### المرحلة 3 — السياق والاستيضاح

- تذكر آخر شهر أو شقة فقط داخل هوية الجلسة الحالية.
- عند «هو دفع كام؟» تستخدم آخر شقة مؤكدة، أما عند وجود أكثر من تطابق فتطلب رقم الشقة.
- عند غياب الفترة في سؤال مالي، تستخدم الشهر الحالي، وتظهر الفترة في عنوان الإجابة.
- عند تعارض فترتين في سؤال واحد، لا تخمّن؛ تعرض سؤال استيضاح.

### المرحلة 4 — جودة وأمان

- إضافة اختبارات للهجات المصرية والعربية الفصحى وأخطاء الهمزات والتاء المربوطة.
- إضافة اختبارات خصوصية للمالك مع كل نية مركبة جديدة.
- قياس نسبة التصنيف الصحيح على مجموعة أمثلة ثابتة قبل كل تغيير.
- إبقاء المساعد حتميًا ومحليًا؛ لا تُرسل نصوص المحادثة إلى نموذج خارجي.

## سيناريوهات RLS المنفذة والمقترحة

كل السيناريوهات تخص جدولَي سجل المحادثة، ولا تمنح المساعد وصولًا مباشرًا إلى الجداول المالية.

| السيناريو | المدير | المالك | النتيجة المتوقعة |
|---|---:|---:|---|
| قراءة محادثته في مبناه | يسمح | يسمح | يرى المستخدم محادثته فقط |
| قراءة محادثة مستخدم آخر في نفس المبنى | يُمنع | يُمنع | صفر صفوف |
| قراءة محادثة من مبنى آخر | يُمنع | يُمنع | صفر صفوف |
| إنشاء محادثة مدير بلا `resident_id` | يسمح | غير منطبق | نجاح للمدير فقط |
| إنشاء محادثة مالك لشقته المرتبطة | غير منطبق | يسمح بعد اكتمال PIN | نجاح |
| إنشاء محادثة مالك لشقة أخرى | غير منطبق | يُمنع | فشل RLS |
| تحديث سياق المدير | يسمح لمحادثته | يُمنع على محادثة ليست له | فشل RLS |
| تحديث `resident_id` إلى شقة أخرى | يُمنع بالـ`WITH CHECK` | يُمنع | فشل RLS |
| إدخال رسالة مستخدم باسم `sender_id` مختلف | يُمنع | يُمنع | فشل RLS |
| إدخال رسالة مساعد باسم مستخدم | يُمنع بقيود الجدول | يُمنع | فشل check constraint |
| قراءة رسائل مرتبطة بمحادثة غير مملوكة | يُمنع | يُمنع | صفر صفوف |
| إدخال رسالة إلى محادثة مبنى آخر | يُمنع | يُمنع | فشل RLS |
| الوصول المجهول `anon` | يُمنع | يُمنع | لا grants ولا صفوف |
| حذف رسالة أو محادثة مباشرة | يُمنع | يُمنع | لا توجد صلاحية DELETE |

## تشغيل الفحوصات

```sh
npm test -- tests/assistant-chat-rls-policy.test.cjs tests/assistant.test.cjs
npm run typecheck
```

اختبار SQL التكامل الكامل يُشغّل داخل بيئة Supabase المحلية بعد تحميل fixture المستخدمين والمباني، ويجب أن يثبت كل نتائج الجدول أعلاه. لا يُستخدم `service_role` في اختبار عميل؛ يستخدم الاختبار `authenticated` مع `request.jwt.claim.sub` مختلفًا لكل سيناريو.

## آلية تأكيد عمليات الكتابة داخل عم عبده

عم عبده لا يكتب مباشرة من نص المستخدم. مسار الكتابة يمر بالمراحل التالية:

1. **التحليل:** `parseAssistantOperationCommand` يحول الطلب إلى مسودة من نوع `income` أو `expense` أو `adjustment` أو تعديل بيانات الشقة.
2. **التحقق من النقص:** `assistantOperationMissing` يحدد المبلغ والمالك والشهر وطريقة الدفع والسبب والوصف المطلوب، ويطلب الناقص في رسالة لاحقة.
3. **المعاينة:** `buildAssistantOperationPreview` يحفظ المسودة في `assistantOperationDraft` ويعرض المالك/الشقة والمبلغ والفترة والصندوق والغرض، دون تعديل `state`.
4. **التأكيد النصي:** لا يبدأ التنفيذ إلا بعد عبارة صريحة مثل «أكد التسجيل». عبارة «إلغاء» تمسح المسودة ولا تغيّر البيانات.
5. **المسار الرسمي:** `confirmAssistantOperation` يفتح مسار النموذج الرسمي مخفيًا، ثم يستدعي `handleIncomeSubmit` أو `handleExpenseSubmit` أو `handleAdjustmentSubmit`. بذلك تبقى قواعد التحقق والصندوق والتدقيق في مكانها الأصلي.
6. **التحقق بعد التنفيذ:** يقارن المساعد عدد السجلات أو لقطة بيانات الشقة قبل وبعد الحفظ. لا يعرض «تم الحفظ» إلا إذا ثبت التغير؛ وإلا يعيد المسودة ويعرض رسالة فشل.
7. **تجاوز رصيد الخزنة:** المصروف الذي يتجاوز الخزنة الرئيسية يعرض الرصيد قبل/بعد ويطلب تأكيدًا صريحًا؛ الصندوق المقيّد غير الكافي يمنع التنفيذ حتى تعديل المبلغ أو الصندوق.

لا توجد أزرار تنفيذ مخفية داخل فقاعات الرد، ولا يستطيع المالك تشغيل هذا المسار. زر «فتح النموذج» مسار مراجعة منفصل، وليس تأكيدًا للحفظ.

## مصفوفة اختبارات Playwright الحرجة

توجد السيناريوهات في `e2e/assistant.spec.js` وتشمل:

- سؤالًا مركبًا باللهجة المصرية عن المصروفات والمتأخرات والخزنة، مع التحقق من الأقسام الثلاثة.
- سؤالًا مركبًا من المالك، مع التحقق من رفض بيانات الإدارة وعدم ظهور أرقام أو سكان آخرين.
- طلب تحصيل ناقص يستكمل المالك وطريقة الدفع في رسالة ثانية، ثم يثبت عدم الكتابة قبل التأكيد والكتابة بعده.
- معاينة مصروف ثم إلغاء نصي، مع مقارنة نسخة `state` قبل وبعد.
- الطلبات المباشرة المؤكدة، ومسودة الإعلان، ومسار فتح النموذج، واختبارات القراءة فقط الموجودة مسبقًا.

لتشغيل هذه المجموعة:

```sh
npx playwright test e2e/assistant.spec.js --grep "compound colloquial|owner compound|incomplete write|typed cancellation"
```
