# آلية التحديث التلقائي لمنزل

> مرجع فني كامل: البنية، خطوات التثبيت والتكوين، تحديث النظام مستقبلًا، وتوافق معايير الويب وPWA.

## 1. الهدف

ضمان وصول أي إصدار جديد إلى متصفحات العملاء **فور نشره على `main` دون أن يمسح أحد ذاكرة التخزين المؤقت يدويًا**. تتحقق ثلاثة عناصر معًا من ذلك:

1. **بصمة محتوى (content hash)** لكل أصل ثابت، تتغيّر فقط عند تغيّر المحتوى فعليًا.
2. **Service Worker** هو طبقة الكاش الفعلية على GitHub Pages، ويقدّم الأصول المُبصّمة بلا شبكة ويعيد التحقق من الصفحة.
3. **إشعار داخل التطبيق** يخيّر المستخدم بين التحديث الآن أو لاحقًا، مع كشف دوري كل 30 دقيقة وتطبيق تلقائي عند أول فرصة مناسبة.

## 2. البنية

| الطبقة | الملف | الدور |
|---|---|---|
| مولّد الإصدار | `scripts/build-index.mjs` | يبصم الأصول، يشتق الإصدار، ويحدّث `index.html` و`sw.js` و`js/telemetry.js` |
| رأس الصفحة | `index.html` (مولَّد) | يربط كل أصل ثابت بمعامل `?v=<hash>` |
| الأصول الثابتة | `css/`، `js/`، `icons/`، `manifest.json` | تحمل بصمة SHA-256 مختصرة إلى 10 خانات ست عشرية |
| الكاش الحقيقي | `sw.js` (مولَّد) | `CACHE_NAME` = الإصدار، و`APP_SHELL` يضم كل أصل ببصمته |
| مندوب التسجيل | `js/sw-register.js` | يفحص كل 30 دقيقة، يعرض بطاقة التحديث، ويطبّق التحديث عند الخمول |
| الإصدار للمتتبّع | `js/telemetry.js` (مولَّد) | `const RELEASE` و`window.MANZIL_RELEASE` لتحميل الوحدات عند الطلب بالبصمة الصحيحة |
| إشعار الأخطاء | جدول `client_errors` | كل خطأ يحمل قيمة `release` لمعرفة الإصدار الذي أنتج الخطأ |

### الإصدار المشتق

- بصمة كل ملف: `sha256(content).slice(0, 10)` بعد تجريد ما يكتبه السكربت (`?v=` وقيم `RELEASE`/`CACHE_NAME`) حتى لا تعتمد البصمة على نفسها.
- الإصدار: `manzil-<10 hex>` مشتق من قائمة `(اسم الملف، بصمته)` لكل الأصول.
- الوحدات المحمَّلة عند الطلب في وقت التشغيل (`js/telemetry.js`، `js/subscription-rates.js`) تأخذ الإصدار المشترك بدل بصمتها، لأن المتصفح لا يقرأ لها `?v=` من `index.html`؛ تقرؤه من `window.MANZIL_RELEASE`.

### سياسة الكاش

| النوع | السياسة | المبرِّر |
|---|---|---|
| أصول تحمل `?v=` | `max-age=31536000, immutable` | الرابط يتغيّر مع المحتوى، فلا حاجة لإعادة تحقق |
| الصفحة الرئيسية | `max-age=3600, must-revalidate` | ظهور الإصدار الجديد خلال ساعة كحد أقصى حتى بلا Service Worker |
| `sw.js` | `no-cache` | لا يجوز تخزين العامل نفسه ليلتقط آخر إصدار فورًا |

**GitHub Pages لا يدعم ترويسات مخصّصة**، لذلك الطبقتان العمليتان هما: سياسة Service Worker (cache-first للمُبصّم، وrevalidate للصفحة) وملف `_headers` الجاهز للنقل إلى Netlify أو Cloudflare Pages. الجزء 3 من هذه الوثيقة يشرح الفرق.

## 3. التثبيت والتكوين

### أ. الاستضافة الحالية (GitHub Pages)

لا خطوة يدوية: النشر يقع على `main`، والبناء يعمل محليًا ثم يُلتزم الناتج.

```sh
npm run build:index   # يحدّث index.html وsw.js وjs/telemetry.js للإصدار المشتق
npm run check:index   # يفشل إن كان أحد الملفات المولَّدة غير مطابق
```

`npm run check:index` يعمل داخل `quality-checks.yml`، فأي `index.html` قديم يوقف الـPR. **لا تُحرّر الملفات المولَّدة يدويًا.**

### ب. النقل إلى Netlify أو Cloudflare Pages

أضف ملف `_headers` في الجذر (موجود مسبقًا). المضيف يطبّق عندها:

- `public, max-age=31536000, immutable` على `css/*` و`js/*` و`icons/*` و`manifest.json`.
- `public, max-age=3600, must-revalidate` على `/` و`index.html`.
- `no-cache` على `sw.js`.

هذان المضيفان يولّدان `ETag` تلقائيًا للأصول الثابتة، فيكتمل الطلب: بصمة في الرابط + `Cache-Control` صارم + `ETag` لإعادة التحقق.

## 4. دورة التحديث

1. **بناء:** يشتق `build-index.mjs` إصدارًا جديدًا ويُبصم كل الأصول.
2. **نشر:** push إلى `main` → GitHub Pages يخدم الملفات الجديدة.
3. **فحص دوري:** `sw-register.js` ينادي `registration.update()` عند `pageshow` و`focus` و`visibilitychange`، وكل **30 دقيقة** أثناء بقاء الصفحة مرئية.
4. **تثبيت العامل الجديد:** `install` يخزّن كل `APP_SHELL` (متسامح مع 404) ثم `skipWaiting()`، و`activate` يحذف كاشات `manzil-*` القديمة ثم `clients.claim()`.
5. **إشعار:** عند `controllerchange` تظهر بطاقة `role="status"` منخفضة التأثير تحمل زرّي:
   - **تحديث الآن** → `location.reload()` فورًا.
   - **لاحقًا** → تُغلق البطاقة ويُؤجَّل التحديث للجلسة الحالية (يُطبَّق عند إعادة الفتح).
6. **تطبيق تلقائي:** إن لم يختر المستخدم شيئًا، يُعاد التحميل عند أول لحظة خمول (لا نافذة مفتوحة ولا حقل قيد الإدخال). عند وجود عمل غير محفوظ تبقى البطاقة ظاهرة بدل مقاطعة المستخدم.

حالات الحماية:

- لا يُعاد التحميل أبدًا أثناء نافذة مفتوحة (`[role="dialog"]:not(.hidden)`) أو حقل مملوء ونشط.
- أول تثبيت لا يسبب إعادة تحميل (يُفرَّق بين `hadController` والتحكم اللاحق).
- البطاقة تظهر مرة واحدة، و«لاحقًا» يمنع إعادة ظهورها حتى إعادة تحميل الصفحة.

## 5. تحديث النظام مستقبلًا

- **تعديل القالب أو الأصول:** حرّر `src/` أو `css/`/`js/` ثم `npm run build:index`. البصمة تتغيّر تلقائيًا، ولا تُلمس أي قيمة إصدار يدويًا.
- **إضافة أصل جديد:** ضعه في `css/` أو `js/` أو `icons/` أو أضفه إلى `ASSET_FILES` في `build-index.mjs`؛ إن كان يُحمَّل عند الطلب فسجّله في `SHARED_RELEASE_ASSETS`.
- **تعديل سياسة الكاش:** حدّث `_headers` ووثّق التغيير في القسم 2، وأبقِ `sw.js` متسقًا.
- **تعديل دورة الفحص:** الفاصل الزمني وأزرار البطاقة في `js/sw-register.js`؛ أي تغيير سلوكي يحتاج تحديث `tests/service-worker.test.cjs` و`e2e/service-worker-update.spec.js`.
- **إبطال الكاش كاملًا عند الحاجة القصوى:** غيّر `APP_CACHE_PREFIX` في `sw.js` (يمسح كل الكاشات القديمة عند التنشيط).

## 6. التوافق مع معايير الويب وPWA

- **Secure context إلزامي:** Service Worker يعمل على HTTPS أو `localhost` فقط.
- **PWA:** `manifest.json` و`theme-color` و`apple-mobile-web-app-*` موجودة، والكاش يغطي هيكل التطبيق كاملًا فيعمل دون اتصال بعد أول زيارة.
- **التدريج:** `skipWaiting` + `clients.claim` + `controllerchange` نمط قياسي في Chrome وEdge وFirefox (المتصفحات المبنية على Chromium/Gecko). Safari/iOS يدعم Service Worker منذ 11.1 ودورة التحديث نفسها؛ الإشعار الداخلي لا يعتمد على Notification API، فيعمل في كل المتصفحات بلا أذونات.
- **CSP:** `worker-src 'self'` و`manifest-src 'self'` مسموحان في وسم CSP داخل `index.html`.

## 7. الاختبارات والأداء

- **وحدات Node:** `tests/service-worker.test.cjs` يثبت صلاحية `sw.js`، ووجود كل الوحدات في `APP_SHELL` ببصماتها، وسياسة cache-first للمُبصّم، وفاصل الـ30 دقيقة، وعقد أزرار البطاقة. التشغيل: `npm test`.
- **E2E (Chromium، سطح مكتب وجوال):** `e2e/service-worker-update.spec.js` يثبت ظهور البطاقة، وأن «لاحقًا» لا يعيد التحميل، وأن «تحديث الآن» ينقل الصفحة إلى الإصدار الجديد. التشغيل: `npm run e2e`.
- **ميزانية Lighthouse:** `.github/workflows/lighthouse.yml` يعمل على `lighthouserc.json` ويطبق ميزانية أداء (performance ≥ 0.85، accessibility ≥ 0.9، best-practices ≥ 0.9، seo ≥ 0.9، وحجم الصفحة ≤ 2MB). العتبات حاليًا `warn` لتثبيت خط الأساس؛ تُرقّى إلى `error` بعد استقرار القياس على المضيف الفعلي.
- **تأثير التحديث على التحميل الأولي:** الأصول المُبصّمة تُخدَم cache-first بلا شبكة، والصفحة وحدها تُعاد التحقق منها، فيبقى التحميل الأول شبكيًا والإعادات لاحقة أسرع.

## 8. استكشاف الأخطاء

| العَرَض | الفحص |
|---|---|
| التحديث لا يظهر | افتح DevTools ← Application ← Service Workers وتأكد من التسجيل والتنشيط، ثم راجع `CACHE_NAME` في `sw.js` مقابل السابق |
| `check:index` يفشل | شغّل `npm run build:index` والْتَزم الناتج |
| البطاقة لا تظهر | تأكد من تنفيذ `sw-register.js` (يبدأ بـ`?v=`) ومن أن الصفحة ليست أول تثبيت (`hadController`) |
| إعادة تحميل متكررة | تحقق أن نمط أول تثبيت لم يُخفَّض: `hadController` و`controllerChanges` في `js/sw-register.js` |
| أصول لا تُخَزَّن | راجع `APP_SHELL`؛ التخزين متسامح مع 404 عمدًا فلا يفشل التثبيت كله |
