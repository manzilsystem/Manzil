# خطة تطوير وإصلاح Manzil

**آخر تحديث:** 3 نوفمبر 2026  
**النطاق:** الخدمات المجانية فقط.  
**أسلوب التنفيذ:** تغيير محدود في كل مرة، فرع مستقل، اختبارات، مراجعة، ثم دمج. لا تغييرات إنتاجية حساسة دون ضرورة وتحقق.

## الحالة التنفيذية المختصرة

| المجال | الحالة |
|---|---|
| المصادقة والجلسات وقفل الواجهة | مكتمل مع اختبارات |
| عزل بيانات المالك وصلاحيات الكتابة | الإصلاحات الأساسية مكتملة؛ تستمر اختبارات الانحدار |
| الحفظ الذري وسلامة البيانات | مكتمل في مسارات الحفظ الأساسية |
| تاريخ أسعار الاشتراك | مكتمل |
| اختبارات Node وPostgreSQL وCI | مفعّلة وناجحة في آخر تشغيل بعد PR #41 |
| النسخ الاحتياطي اليومي واليدوي | مفعّل ويعمل |
| طلب الاستعادة والتحقق قبل التنفيذ | مفعّل؛ لم تُجر استعادة فعلية |
| مزامنة Releases مع backup_catalog | إصلاحها مدمج؛ مراقبة دورة التنظيف التالية |
| اختبار استعادة معزول end-to-end | مؤجل لعدم وجود بيئة اختبار مستقلة مجانية |
| حماية كلمات المرور المسرّبة | غير متاحة ضمن خطة Supabase الحالية؛ لا تغيير على PIN لإجبار تفعيلها |
| تنظيف الفهارس غير المستخدمة | مؤجل حتى تتوفر قياسات استخدام كافية |

## طريقة العمل والقيود

1. كل تغيير في فرع مستقل وبنطاق واضح، مع اختبارات انحدار.
2. تغييرات قاعدة البيانات تتطلب migration مستقلة ومراجعة أثرها قبل التطبيق.
3. لا تُعدّل بيانات المستخدمين أو الحسابات أو السجلات المالية في الإنتاج لأغراض الاختبار.
4. لا تُحذف فهارس أو سياسات أو نسخ احتياطية اعتمادًا على تحذير آلي فقط.
5. لا يُنفذ Restore على الإنتاج كاختبار؛ الاستعادة تستبدل قاعدة البيانات بالكامل.
6. لا تُنشأ Supabase branches أو موارد مدفوعة؛ المشروع ملتزم بالخدمات المجانية.
7. لا تُعرض أسرار GitHub أو Supabase في المتصفح أو السجلات أو التوثيق.

## ما اكتمل

### 1. المصادقة والجلسات

- معالجة أخطاء الشبكة في تسجيل الدخول وتهيئة الجلسة حتى لا يظل زر الدخول معطلًا عند فشل الاتصال.
- الإبقاء على مستمع تغيّر المصادقة مسجلًا عند فشل التهيئة.
- قفل الواجهة محليًا عند تسجيل الخروج أو انتهاء الجلسة حتى إذا فشل طلب `signOut`.
- مسح بيانات المبنى والمستخدم وحقول كلمة المرور وPIN من الحالة والواجهة عند القفل أو تبديل المستخدم.
- حماية تغيير PIN المالك عبر Edge Function تتحقق من الجلسة والدور وPIN الحالي؛ لا يملك `authenticated` تحديث `profiles` مباشرة.
- بوابة RLS تمنع المالك من الوصول إلى بياناته قبل استكمال تغيير PIN الإلزامي.
- الجلسة تُقفل تلقائيًا بعد خمس دقائق من عدم النشاط.

### 2. الصلاحيات والخصوصية

- سياسات RLS تفصل بيانات المباني والملاك، وبوابة المالك للقراءة فقط.
- إصلاح تجاوز `must_change_pin` وسحب صلاحية تحديث الملف الشخصي مباشرة من المستخدمين المصادق عليهم.
- اختبارات انحدار لتدفقات المصادقة والجلسات وتغيير PIN وقيود الوصول.
- لا تُجر تغييرات إضافية على RLS إلا استجابة لاختبار فاشل أو ثغرة قابلة لإعادة الإنتاج.

### 3. الحفظ وسلامة البيانات

- تنفيذ حفظ ذري للـ snapshot عبر `persist_building_snapshot` مع إصدار الحالة والتحقق من التعارض.
- تحسين سلامة تدفقات الكتابة والعمليات المالية ومنع الكتابات الجزئية في المسارات التي عولجت.
- اختبارات للحفظ والتزامن وسلامة البيانات والتدفقات المالية.
- معالجة تاريخ أسعار الاشتراك: حفظ السعر وتاريخ سريانه واستخدام السعر التاريخي في حساب الأشهر السابقة.
- إزالة RPC قديم بعد استبداله بالمسار الذري الجديد.

### 4. التقارير وتجربة الاستخدام

- دعم الدفعات الجزئية والمتأخرات وتصنيفها واختبار الحالات الحسابية.
- تقارير المتأخرات المجمعة وتصدير CSV.
- دعم نطاقات زمنية تصل إلى 60 شهرًا مع الإبقاء على الأشهر الأقدم ذات السجلات.
- تحسينات إعدادات المبنى والمظهر والحساب والنسخ الاحتياطي، مع ثيمات متعددة وتخطيط متجاوب.
- إضافة اختبارات للواجهة وإعدادات التطبيق والوظائف الأساسية.

### 5. النسخ الاحتياطي والاستعادة

- نسخة PostgreSQL تلقائية يومية الساعة 02:23 UTC (04:23 مصر) باستخدام GitHub Actions.
- نسخ مضغوطة مع SHA-256 وفحص أرشيف `pg_restore --list` قبل الرفع.
- رفع النسخ إلى مستودع GitHub خاص منفصل والاحتفاظ بآخر 30 نسخة.
- فهرس `backup_catalog` في Supabase وطلبات النسخ اليدوي والاستعادة.
- واجهة داخل التطبيق لعرض النسخ وطلب نسخة يدوية وطلب الاستعادة ومتابعة الحالة؛ لا حاجة لفتح GitHub.
- Edge Function تتحقق من JWT ودور المدير والنسخة المطلوبة وتأكيد `RESTORE`.
- عامل الاستعادة يتحقق من SHA الموثوق في الكتالوج، ويقارن الملف، ويفحص الأرشيف قبل التنفيذ.
- حجز ذري لطلبات الاستعادة، ومعالجة الطلبات العالقة وحالات النتيجة غير المؤكدة.
- بعد الاستعادة الناجحة أو النتيجة غير المؤكدة، تُقفل جلسة من بدأ العملية ويُطلب تسجيل الدخول مجددًا.
- مسار النسخ اليدوي يمر عبر queue داخل قاعدة البيانات، ثم dispatch إلى workflow مع request ID، وتحديث حالة الطلب المطابق فقط.
- تنظيف Releases غير المسجلة بعد مهلة أمان 24 ساعة، وتنظيف سجلات الكتالوج التي لم يعد لها Release فقط عند تأكيد HTTP 404. أي استجابة غير واضحة توقف التنظيف بدل حذف البيانات.
- PR #41 دمج إصلاح التوفيق بين الكتالوج وReleases.

**آخر تحقق تشغيلي في 3 نوفمبر 2026:**
- نجح workflow النسخ بعد PR #41، بما في ذلك Dump وUpload وRegister وOrphan cleanup وRetention.
- آخر نسخة مسجلة: `backup-20261103T045656Z`، بحجم 376,855 بايت. قيمة SHA-256 المسجلة تطابق digest ملف dump في GitHub Release.
- أظهر التدقيق 12 سجلًا في الكتالوج و15 Release: 10 سجلات لها Releases مطابقة، وسجلان قديمان بلا Release، وخمسة Releases غير مسجلة. العناصر غير المتطابقة كانت ضمن مهلة الأمان 24 ساعة وقت التدقيق؛ لم تُحذف سجلات أو Releases يدويًا. تُراجع بعد انقضاء المهلة وتشغيل التنظيف الدوري.
- نجاح فحص الأرشيف والـCI لا يثبت نجاح استعادة فعلية. لم تُجر استعادة على الإنتاج أو على بيئة اختبار مستقلة.

## مراحل العمل المتبقية

### المرحلة A — إغلاق تدقيق النسخ

1. مراجعة دورة النسخ التالية بعد مرور مهلة 24 ساعة على العناصر اليتيمة.
2. التحقق من تطابق عدد سجلات الكتالوج مع Releases الفعلية، ومطابقة SHA-256 وحجم ملف dump لكل نسخة مسجلة.
3. التحقق من بقاء آخر 30 نسخة فقط دون حذف النسخ الحديثة أو غير المسجلة حديثًا.
4. عدم تنفيذ Restore فعلي؛ لا توجد بيئة اختبار مستقلة مجانية حاليًا.

**معيار الإغلاق:** لا توجد عناصر أقدم من مهلة الأمان غير مفسرة، وكل نسخة معروضة قابلة للتنزيل ولها checksum مطابق.

### المرحلة B — اختبار الاستعادة دون مخاطرة

1. إعداد إجراء اختبار موثق لاستعادة نسخة إلى قاعدة اختبار منفصلة عند توفر بيئة مجانية آمنة.
2. التحقق بعد الاستعادة من المخطط والجداول وعدد السجلات غير الحساسة وسلامة العلاقات.
3. اختبار دخول المدير والمالك وعمليات القراءة بعد الاستعادة.
4. لا تُستخدم قاعدة الإنتاج لهذا الاختبار، ولا يُنشأ فرع Supabase مدفوع.

**معيار الإغلاق:** نجاح استعادة معزولة موثق. يظل هذا البند مؤجلًا ما دامت بيئة الاختبار غير متاحة.

### المرحلة C — إعدادات المصادقة

- ميزة Leaked Password Protection تتطلب خطة Supabase أعلى من الخطة المجانية الحالية؛ لا يمكن تفعيلها ضمن قيد المشروع الحالي.
- لا نغيّر PIN المالك ذي الستة أرقام ولا نضعف سياسة الدخول لتجاوز القيد.
- يمكن إعادة تقييم الإعداد فقط إذا تغيرت إتاحة الميزة ضمن الخطة المجانية أو تغير تصميم مصادقة المالك دون كسر التوافق.

### المرحلة D — الأداء والاعتمادية

1. متابعة سجلات أخطاء Edge Functions وPostgreSQL ضمن نوافذ زمنية محددة.
2. مراجعة فهارس `unused_index` بعد توافر نشاط فعلي كافٍ؛ لا حذف حاليًا.
3. قياس الاستعلامات البطيئة قبل أي تحسين أو إضافة فهرس.
4. الاستمرار في اختبارات Node وPostgreSQL وواجهات النسخ والاستعادة بعد كل تعديل.

### المرحلة E — تحسينات المنتج المجانية

- مراجعة تجربة الاستخدام على الهاتف: وضوح التنقل، أحجام الأزرار، رسائل الأخطاء، وحالات التحميل.
- مراجعة إمكانية الوصول: ترتيب التركيز، ARIA، التباين، ودعم لوحة المفاتيح.
- تحسين دليل الاستخدام ورسائل التأكيد والتحذير للعمليات المالية والاستعادة.
- تحسين الإقفال الشهري وسجل التدقيق والإشعارات بعد تحديد حالات الاستخدام بدقة.
- كل تحسين يُنفذ منفصلًا ويُختبر قبل الدمج.
